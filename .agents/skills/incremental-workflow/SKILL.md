# Incremental Implementation Workflow

## Purpose

Large implementations require many design decisions at once: architecture, data structures, interfaces, naming, error handling, dependencies, testing strategy, and integration.

Delivering all of those changes in a single step makes the resulting diff difficult to review and makes it harder to catch an incorrect design decision before it propagates through the rest of the implementation.

This workflow therefore breaks non-trivial implementation work into small, independently verifiable units.

The goal is not to minimize the amount of code delivered at once. The goal is to minimize the amount of **unverified design and implementation** delivered at once.

---

# Core Rule

For non-trivial implementation tasks, follow this cycle:

**Plan → Implement one block → Verify → Show diff → Wait for approval → Continue**

Do not implement the entire task end-to-end unless the user explicitly asks for it, for example:

* "Implement everything at once."
* "Do the whole implementation without stopping."
* "Don't pause for review."
* "Give me the complete solution."

A request for the complete implementation overrides this workflow.

---

# 1. Plan

Before modifying any file, present a concise implementation plan.

The plan must include:

### Files

List every file that is expected to be created or modified.

Prefer concrete paths rather than generic descriptions such as "backend files" or "the API."

### Work blocks

Provide a numbered sequence of implementation blocks in dependency order.

Each block must represent a **small, independently verifiable unit of work**.

Good examples:

1. Define the `User` model and validation.
2. Add the repository method for creating users.
3. Add the `POST /users` endpoint.
4. Add endpoint tests.
5. Integrate the endpoint with the frontend form.

Avoid blocks that are merely broad areas of the system, such as:

* "Implement the backend."
* "Finish authentication."
* "Build the frontend."

A block should be small enough that its correctness can be reviewed without reading the entire project.

### Design decisions

Explicitly identify assumptions or ambiguous decisions that could affect later blocks.

Examples:

* Whether validation belongs in the controller or domain layer.
* Whether IDs are generated by the application or database.
* Whether the API should return `404` or an empty collection.
* Whether a new dependency is justified.
* Whether an existing abstraction should be extended or replaced.

Do not silently make a consequential architectural decision when multiple reasonable approaches exist.

### Scope

State which block will be implemented first.

Do not modify files for later blocks during the planning stage.

---

# 2. Implement One Block

Implement exactly one approved block at a time.

### Scope discipline

Do not modify files outside the scope of the current block.

Do not implement future blocks "while you are already there."

Do not refactor unrelated code merely because it could be improved.

If implementation reveals that the original plan is incomplete or incorrectly ordered, stop and explain the necessary plan adjustment before continuing.

### Block size

A block should normally be small enough to review in a few minutes.

If a block becomes substantially larger or more complex than expected, split it into smaller sub-blocks rather than delivering a large batch of changes.

### Dependencies

A block may depend on previously completed blocks, but it should not silently depend on unfinished future work.

At the end of the block, the repository should remain in a coherent state whenever possible.

---

# 3. Verify

After implementing a block, verify it before moving on.

Use the strongest practical verification available for the project:

1. Run relevant tests.
2. Run type checking, linting, or static analysis when applicable.
3. Compile or build the affected project.
4. Perform a focused manual verification when automated verification is unavailable.

Do not claim that something was verified if it was not actually checked.

If verification fails:

* report the failure,
* identify the likely cause when possible,
* fix issues that belong to the current block,
* rerun the relevant verification.

Do not hide test failures behind unrelated changes.

If an existing test or build is already broken before the block, clearly distinguish **pre-existing failures** from **regressions introduced by the current block**.

---

# 4. Review

After verification, show the **actual diff produced by the block**.

The diff is the source of truth.

Do not replace the diff with a prose-only summary.

The review output should include:

### Diff

Show the relevant patch or file changes exactly as they exist after implementation.

### Verification

State which commands were run and whether they passed.

Examples:

```text
Tests: 18 passed
Build: successful
Lint: successful
```

or:

```text
Tests: 16 passed, 1 failed
Build: not run
Reason: the project has an existing compilation error in ...
```

### Notes

Briefly explain any important implementation decision that is not obvious from the diff.

Keep this explanation subordinate to the actual changes.

---

# 5. Stop After the Block

Do not automatically implement the next block.

After presenting the diff and verification results, stop and wait for explicit approval, modification, or redirection from the user.

Valid continuation signals include requests such as:

* "Continue."
* "Proceed."
* "Do the next block."
* "Looks good."
* "Change X and continue."

A neutral acknowledgement or lack of feedback is not approval to continue.

---

# Handling User Corrections

If the user changes a requirement or design decision:

1. Determine whether it affects only the current block or also future blocks.
2. State which planned blocks are affected.
3. Update the plan before implementing dependent changes.
4. Do not silently preserve assumptions that the user has invalidated.

When possible, prefer the smallest change that restores alignment with the user's new requirement.

---

# Handling Uncertainty

Do not stop merely because an implementation detail is uncertain when a reasonable, low-risk assumption can be made.

Instead:

* identify the assumption,
* choose the least disruptive option,
* document it briefly,
* continue within the current block.

However, when an ambiguity could materially change the architecture, public API, data model, compatibility, security, or long-term behavior, surface the decision before implementing dependent blocks.

Do not ask unnecessary clarification questions when the task can be safely advanced through an explicit assumption.

---

# Repository Consistency

At the end of each block, leave the repository as consistent as reasonably possible.

Prefer:

* compilable code,
* passing relevant tests,
* valid imports and references,
* no temporary debugging code,
* no partially implemented interfaces,
* no knowingly broken state.

An intermediate state is acceptable only when the current block inherently requires a temporary transition, and that state must be explicitly identified.

---

# Refactoring Rule

Do not introduce unrelated refactors during implementation.

A refactor is justified within the current block only when it is:

* necessary for the block to work,
* directly required by the design being implemented, or
* required to preserve correctness.

Otherwise, record it as a separate future block.

This keeps the diff attributable to one purpose.

---

# Existing Code and Tests

Before changing existing behavior, inspect the relevant code and tests.

Prefer extending existing abstractions and conventions when they are appropriate.

Do not introduce a new architectural pattern solely because it is technically possible if an existing project convention already solves the problem adequately.

When behavior changes intentionally, update or add tests that explicitly capture the new behavior.

---

# Completion Criteria

The task is considered complete only when:

* every planned block has been implemented or intentionally removed,
* relevant tests and verification steps have been performed,
* the final repository is in a consistent state,
* no known required functionality remains silently unfinished.

At the end of the final block, provide the final diff and verification results for that block, followed by a concise overall status summary.

---

# Exceptions

Do not apply the full incremental workflow to:

* one-line fixes,
* trivial renames,
* typo corrections,
* narrowly scoped questions,
* explanations that do not require code changes,
* changes where the user explicitly requests a complete implementation in one pass.

For borderline cases, prefer the incremental workflow when the task involves meaningful architectural or behavioral decisions.

---

# Guiding Principle

**Optimize for reviewability, not for the number of files changed per response.**

Every block should answer three questions:

1. **What changed?**
2. **How was it verified?**
3. **What remains to be decided or implemented?**

## Never advance to the next block merely because the current implementation appears correct. Advance because the current block has been made explicit, verified, and approved.
